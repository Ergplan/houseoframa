# Known gaps

Updated in the same commit as the code that opens or closes a gap.

- EkBill has no `data-rama-figure` instrumentation. Its five headline figures are traced by an overlay in its working clone (`.rama/figures.json`, hand-written harnesses); the other 156 figures on its 12 captured screens are untraced (at 4f28628). Instrumenting EkBill itself (HOUSE-STYLE §1–2) is the EkBill team's work.
- No city layout; a single building per site. EkBill (916 bricks) fits in one building about 1,500 scene pixels wide; at fit-to-screen its bricks are about half size, so `Zoom 1:1` or the brick finder is the way to reach a small one.
- (Stage 0) The `stack` compose profile (app and watcher in containers) is validated with `docker compose config` but has not been run end to end; `pnpm dev` is the tested path.
- (Stage 0) The Stage 0 e2e test runs on this repository's own app; there is no target repository in Stage 0.
- (Stage 1) EkBill's remote needs credentials, so CI cannot clone it: its extraction is exercised on this machine only. Procurement Studio (public) is the golden target in CI.
- (Stage 1) Imports are read from JS/TS sources only: CSS `@import`, MDX imports and `import()` with a computed path are not edges. A computed `process.env[x]` is flagged `envDynamic` rather than named.
- (Stage 1) A brick's history is its current path only: commits made under a previous name (before a rename) are not counted in `changes` or `firstCommit`.
- (Stage 2) EkBill's `.rama/` (layers, confirmed 2026-10-20 by Rachit Agarwal; glossary; purposes) lives only in the working clone `work/ekbill/repo`. **When the Stage 4 gate lands, the EkBill team commits `.rama/` into EkBill** so its CI and every fresh clone see it. Until then a fresh `rama site add` of EkBill starts without it.
- (Stage 2) Confirmations are written to the target's working copy only. Committing them to the target is the target team's act (House of Rama never pushes), so a fresh `rama site add` of the same repository starts without them.
- (Stage 2) The canvas is not readable by a screen reader. Its label states the size of the site, and the brick finder and the inspector give keyboard and screen-reader access to every brick.
- (Stage 2) EkBill is not in CI (its remote needs credentials). `/site/ekbill` is exercised on this machine. The Stage 2 e2e runs on this repository and on a throwaway fixture site.
- (Stage 3) `gpt-6.1-sol`'s price in `packages/model/src/prices.ts` is taken from third-party price lists that agree with each other; OpenAI's own pricing page refused automated access. The row is marked `fromVendor: false` until checked against the vendor's page or invoice. Costs use list prices: cache discounts are not applied.
- (Stage 3) Drafting follows `export * from` and `export { … } from` (up to 6 hops); a symbol re-exported through `export default` of another module, or built at run time, is not followed and its edge stays without English.
- (Stage 3) Capture photographs only what a target draws with no secrets. EkBill's screens show its sample shop as a look (`?as=owner`; since 4f28628 a signed-out visitor is sent to `/welcome`), not a signed-in business's live data, so the traced values are the fixture's. Live-data screens need a seeded demo database that the capture can start, and that is not built.
- (Stage 3) Untraced figures are detected from text: amounts with a currency sign, percentages, bare numbers, and (conservatively) numbers inside words. A canvas, a video, a frame, and an image or CSS background image with a side longer than 24 px are marked untraced as a whole, since their content cannot be read. Images no larger than 24 × 24 px are icons and are not marked, by design: they cannot hold a figure a person reads. Detection reads the page's text nodes, form values, CSS-generated text (quoted strings and `attr()`) and open shadow roots. What it cannot read, it marks untraced as a whole: CSS `counter()` content ("generated content"), and a defined custom element without an open shadow root, which may draw in a closed one ("component"). An element holding two separate amounts in its own text is marked once, not twice. The conservative pass also marks numbers that are not figures, such as a house number in an address or a step number ("01 / KISKA BILL"), so the honest rate's denominator is slightly high. So does the drawing rule: every inline SVG larger than an icon is marked, decorative ones included (EkBill's hero wave, for instance).
- (Stage 3) An overlay figure's selector is checked only by its re-execution matching the screen. If EkBill changes its markup the selector may find nothing; the figure then simply does not appear on that screen and is not counted.
- (Stage 3) This repository (`self`) has no `.rama/screens.json`, so its Showroom says nothing has been captured. Instrumenting House of Rama's own Trust report per HOUSE-STYLE is not done.
- (Stage 7) EkBill is retired as a target. Its tests are replaced by the sample product's, which run in CI: capture and re-execution in Test drive (`packages/workbench/test/testdrive.test.ts`), the walkthrough and the gate in `tests/stage-4.sample.e2e.test.ts`, the real audit in `tests/stage-5.sample.vendor.e2e.test.ts` (@vendor). `work/ekbill` and its reports stay as history; the site still opens on this machine.
- (Stage 4) The gate workflow is in EkBill's working clone only (`work/ekbill/repo/.github/workflows/rama-gate.yml`), with its `.rama/` records. EkBill's team commits both, and makes "rama gate" a required check in branch protection (a setting outside the repository). Until then EkBill merges without the gate.
- (Stage 4) In CI the target's own tests (the pull request's code) produce the test report, in a job of their own. A pull request can make its tests report passes falsely, and then the test path lets a screen through; it cannot reach the gate or the signature file at the base. A signature line added in the pull request itself counts only if it carries House of Rama's seal, when the workflow gives the gate the public key (gaps 1). Without a key, no signature counts (only passing tests do), and the app refuses to sign. Signatures made before the key existed carry no seal, and count for nothing once a key is set: they have to be signed again. The key cannot be rotated in place; a new key means re-installing the workflow and signing again.
- (Stage 4) Discovery turns are stored in Postgres only; they are not mirrored to the target (decision cards and signatures are). Dictation uses the browser's speech recognition where it exists (Chrome); elsewhere the member types.
- (Stage 7) A card is withdrawn only by "Scrap everything", which withdraws every card in force; one card cannot be withdrawn alone (it is superseded by an open one instead).
- (Stage 5) The audit's checks are pattern checks: a swallowed error, an `any` or a constant is found, not judged. Coverage per brick is "a passing test imports it", not lines executed. The auditor may lower a verdict with a reason, and a person reads it.
- (Stage 5) `long-unauth-route` recognises a sign-in check by name (`auth`, `session`, `getViewer`, `cookies()` and similar) in the route file. A check hidden behind another name, or in middleware, is not seen, and the route is reported.
- (Stage 5) The audit runs the target's scripts on this machine with PATH and HOME only. A target whose tests need a database or keys reports those tests as failed or not run. EkBill's `test` script runs its unit project only, so its integration tests are not part of its audit.
- (Stage 5) This repository's own audit has zero defects. Its notes stand: untested code bricks, silenced lint with reasons, empty catch blocks in scripts and test helpers, environment fallbacks for local defaults, unsigned screens, and drafted phrases nobody confirmed. The latest report lists them at `/site/self/audit`.
- (Stage 7) **Picking a name is not security.** Anyone who can reach the app can pick any name in `members.json`, and a trainer's name opens every site, the keys in Settings (masked, but replaceable) and the campus. That is version 1 by design (rule 11: on a laptop, among ourselves). On the box at a public address it means anyone on the internet can act as anyone; put it behind a network you trust, or switch the floor edition's `AUTH_MODE=password` on, until the floor edition's sign-in is built. People are added by editing `members.json`, not from the app.
- (Stage 7) With `AUTH_MODE=password` the floor edition's sign-in by username and password from `RAMA_ACCOUNTS` returns (Gaps 1). Those passwords sit in plain text in `.env`, there is no lockout after repeated failures (only a half-second pause), and accounts cannot be changed from the app.
- (Stage 7) A key's light is the outcome of its last Test, kept in Postgres. A key that stops working later (revoked, out of credit) shows green until it is tested again or a call fails.
- (Stage 7) Jobs (refresh, photograph, tests, audit, Test drive) run inside the app's process. A restart cuts a running job off; its page then says it was interrupted and offers to run it again. Two app processes would not see each other's running jobs.
- (Stage 7) Test drive and "Photograph the screens" build a product with the packages House of Rama already has installed (Next.js 16.3.8, React 19.3.0, Drizzle, Vitest), linked into its `node_modules`, so no network is needed. That works for the sample product and for products on exactly those versions; any other product runs its own install (`npm install` from its screens file), which needs the network. Its build uses webpack, because Turbopack refuses packages outside the project root (DECISIONS).
- (Stage 7) Without the OpenAI key, Test drive's audit is passed on by a stand-in that adds nothing to the checks. The report says so ("stand-in", "test drive, no auditor key"); it is not an audit by a second vendor, and "Call the audit" on a real product refuses to run without the key.
- (Stage 7) Product repositories are created private, under the GitHub account in Settings, with a classic or fine-grained token that may create repositories there. Branch protection (making "rama gate" a required check) is not set by House of Rama: it is a repository setting, and the token may not have the right to change it. The real GitHub test (`packages/workbench/test/github.vendor.test.ts`, @vendor) has not been run: it needs a token, and it leaves a repository behind.
- (Stage 7) The merge gate still credits a changed screen through test files that import its changed code bricks and pass (Invariant 4, unchanged). The three states use the stricter rule (a test that renders the screen, visits its route, or calls each of its figure functions). Bringing the gate onto the same rule is open.
- (Stage 7) What a test executed is recorded per test file from V8 coverage, which needs Vitest's thread pool (`--pool=threads`, passed by "Run the tests") so that each test file has a worker of its own. A product on another test runner records nothing, and none of its screens can be Verified until one is supported. A screen exercised only by a browser test that visits its route is not Verified either, because the run cannot show the visit.
- (Stage 7) The trainer console's acts that later stages bring (Close ideation, Start build, Pause build) are shown greyed with the stage that enables them.
- (Stage 6) **There is no pod yet; the box stack runs on the build VM** at http://34.131.209.81:3389 (since 2026-10-24, `.env.box`). Port 3389 is used because the default network's firewall already opens it to every VM. Port 80 would need the VM's `http-server` tag ("Allow HTTP traffic"), or a firewall rule, and this machine's credentials cannot add either. The external IP is ephemeral: it can change if the VM is stopped and started, unless a project owner promotes it to a static address. The site is plain http, so passwords cross the network unencrypted.
- (Stage 6) The box serves plain http on `APP_PORT`; https is a reverse proxy in front of it (docs/DEPLOY.md), not part of the compose file.
- (Stage 6) Backups are copied off the box only when `BACKUP_COPY_COMMAND` is set (gaps 1). Where they go, and the tool and credentials that take them there, are the box owner's choice; none is set up.
