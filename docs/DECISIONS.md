## 2026-10-23 — Stage 6: the floor edition

- **Sign-in is an email link** (no passwords), as locked.
  - **Links:** the token is 32 random bytes, and only its sha256 is stored. A link works once (spent by a single conditional update, so two simultaneous clicks cannot both succeed) and for 15 minutes.
  - **Sessions:** a 30-day httpOnly, SameSite=Lax cookie, Secure when the app's address is https. The session is stored as a hash too, and sign-out revokes it.
  - **The link request** answers the same whether or not the address belongs to a member.
- **Mail by SMTP, with a local outbox.** With `SMTP_URL` set, the link is mailed. Without it (this machine), it is written to the server's log. `pnpm rama-member link <email>` prints one for whoever has this machine's shell. Which mail service the floor uses is the user's choice.
- **A site belongs to one member, and another member's site does not exist.** Every page under /site redirects to /login without a session, and answers not found for a site the member does not own. Every site route answers 401 without a session and 404 for another's site. /api/health stays public. A manager sees the campus, not other members' sites.
- **Members are added from the command line** (`pnpm rama-member add <email> <name> [--manager]`). The pre-Stage 6 local member keeps their sites and gains an email: for this build, the user's account email.
- **The pod light is read from the records**, by `podLight()` in the metrics engine:
  - **off:** no booking now;
  - **pink:** game mode;
  - **green:** every screen signed at the site's current commit, and that commit's audit found no defect;
  - **amber (awaiting sign-off):** the screens are photographed at the current commit, and one is not signed there;
  - **blue:** otherwise, work in progress. That includes code ahead of its photographs, and screens signed but not yet audited.
    The prompt names the colours, not when each applies; this reading makes each one a fact a person can check.
- **The pod controller authenticates with a bearer token** (`RAMA_POD_TOKEN`). It sees the light, the shift, the end of the booking and the site's name, not who booked it. Without a configured token the route answers 503, rather than serving the floor to anyone.
- **Bookings cannot double-book a pod.** The overlap check and the insert hold the pod row's lock. A work booking names a site the member owns; game mode names none.
- **The triptych is three full pages in frames** (Discovery, Site, Showroom), side by side when the window is at least 2400 px wide (three 4K screens), tabs otherwise. Each page keeps its own behaviour, narration included.
- **Sign-ins and sessions are not append-only.** A link is spent and a session revoked by an update (`used_at`, `revoked_at`): they are credentials, not a record anyone signs. Like `people`, they carry no site (`site_id` is null).

## 2026-10-23 — Stage 5: the audit

- **The checks run the target's own scripts.** `typecheck`, `build` and `test` are the scripts in its `package.json`, run with the package manager its lockfile names, in its checkout, with PATH and HOME only (no House of Rama secret reaches the target). A target without such a script gets the check reported as not run, never as a pass. This repository gained a root `build` script (`NEXT_DIST_DIR=.next-build`) so its own audit runs the build, away from the dev server's `.next`.
- **Coverage per brick is read from the test report and the import graph**, not from instrumented line coverage. A code brick is covered when a test file that imports it passed. When only failing tests import it, it is a defect, and so is each failing test file. When no test imports it, it is a note. Line coverage would need each target's coverage tooling, and would be a different number.
- **Severity.** Defects: a compiler error, a failed build, a failing test, a long route with no sign-in check, and a fixed position taken from a sorted list. Everything else is a note: silenced lint, swallowed errors, `any`, constants in formula files, browser storage, environment fallbacks, unsigned changes, unconfirmed phrases, open decisions. They are true observations, not proof that something is wrong. A fixed position read after the list's length is tested is not flagged (after the first real run, where EkBill's `matchCustomer` reads `close[1]` only when `close.length > 1`).
- **Formula files are the files of the site's traced figures** (the capture's mappings). A site with no traced figure has no formula file, and the report says so.
- **The auditor cannot add a defect, by construction.** Its reply has no field for a finding. `applyReply()` refuses a reply that names a finding it was not given, raises a verdict, cites a commit that is not in the history, or calls an alteration a defect without citing a defect the checks found and it kept; then nothing is stored. It may lower a verdict, with a reason: both the checks' verdict and the auditor's reason are stored. It is given the totals so it never counts lists (after the first EkBill run, where it said 130 decisions for the 129 it was sent).
- **Signed means traceable to the auditor's own call.** The report names the vendor, model and `model_calls` row. `inputs_hash` is the sha256 of the canonical JSON the auditor received. `verifyReport()` recomputes it from that row, and the report page verifies it on every view.
- **Sign-offs confirmed or rejected by plain code**: a signature in force is rejected when a brick of its screen carries a defect in the audit, and confirmed otherwise.
- **The auditor's words are drafted text** (after the Stage 5 reviewer's first run). Its narration, alterations, time machine and reasons for lowering a verdict are shown as "drafted by <vendor model>; unconfirmed" until a named person confirms them: an append-only `audit_confirmations` row, audited by trigger, made from the report page as the local member. The checks' findings are not drafted; they are plain code.
- **An audit's totals come from the metrics engine** (`auditCounts()`, `auditFloorCounts()` in `packages/blueprint/metrics`), like every other figure (Invariant 7), after the same review.
- **Scripts run only on the audited code** (same review). An audit extracts the Blueprint from the checkout as it is, and runs `typecheck`, `build` and `test` only when the checkout is at that commit, with no change to a tracked file unless the Blueprint was read from the working tree. Otherwise those checks are reported as not run, with the reason. A test command that exits non-zero is a defect: whether no test file failed, or it failed before writing a report. A run that reports no test file is a note. Exit 0 with no report credits nothing and is reported as not run.
- **A position is spared only by a bound that covers it.** For example `close.length > 1` before `close[1]`, in the true branch of an `if` or `? :`, on the right of an `&&`, or after an `if (…) return` or `throw` whose condition rules the short list out. A test that does not cover the position, does not exit, or guards the other branch leaves the finding standing.
- **A brick the audit did not see gets no badge.** The replay skips it and says how many there are, and the panel says when the building has moved past the audited commit.
- **Audits are run from the command line** (`rama-audit run <site>`): a run builds and tests the target for minutes. The app shows and replays the latest audit, and does not start one.

- **Continuing without stopping between stages**, on the user's word after Stage 3 ("Yes and please continue for next 12 hours", 2026-10-22). - **Append-only by trigger, not by a Postgres rule.** The stage says "a Postgres rule (no UPDATE/DELETE)". A rule silently turns an UPDATE into nothing; a trigger refuses it with an error, so a mistaken write fails loudly. The same `rama_refuse_change()` trigger as `model_calls` and `audit_log` covers `discovery_sessions`, `discovery_turns`, `decisions` and `signoffs` (UPDATE, DELETE, TRUNCATE). Every insert into `decisions` and `signoffs` appends `audit_log` by trigger, in the same transaction, so no code path can skip it.
- **A withdrawal is a signature row with `withdrawn: true` that supersedes the one in force.** The stage lists `supersedes?`; it does not say how a person takes a signature back without signing again. A chain may not fork (a signature is superseded at most once) and may not jump targets (`checkChain()`).
- **The mirror is written only from committed rows, under one lock per site** (after the Stage 4 reviewer's first run). A site's ceremony writes take a Postgres advisory lock. The chain check and the insert run in one transaction, and the file is brought up to the committed rows in a second (`syncMirror`). So `.rama/*.jsonl` never holds a row the database does not, two writers never append at once, and two concurrent supersessions cannot both pass the check. A unique index on `supersedes` refuses a fork even without the lock. A line that could not be written (a crash, a full disk) is appended by the next write: the mirror can lag, but is repaired forward and never rewritten. The first design wrote the line inside the transaction and rewrote the file on rollback, which could erase another writer's committed line.
- **The gate's test rule.** The stage says "a passing test file among its bricks". A screen's bricks are what it renders; test files are never among them. The gate reads the rule as: every changed code brick of the screen is imported by a test file that passed in the test report (`--test-report`, vitest or jest JSON). Without a report, only signatures count. A signature counts when it is in force and names a commit at or after the screen's last change in `base..HEAD`.
- **The gate cannot be switched off from inside the target.** It reads code, history and `.rama/signoffs.jsonl` only, no file of settings and no environment variable, and it fails when a signature line present at the base was changed or removed. A screen counts if it is at HEAD or at the base, with its bricks from either, so removing a screen or deleting a brick is a change that needs a signature. History is read along the first-parent chain with each merge's full diff, and a rename names both paths, so an edit that arrives only by a merge, or a screen renamed away, is seen too (after the reviewer's second run). The tests job names each test file by its repository path before the report reaches the gate's runner. Its workflow runs on `pull_request_target`, so the copy on the base branch judges a pull request, and in two jobs on two runners. The target's tests (its code) run in one job, with a read-only token and no secrets, and produce only a report. The gate job never runs the target's code and runs House of Rama at a pinned ref, so an install script in a pull request cannot reach the gate. (Both after the Stage 4 reviewer's first run.)
- **Signatures name Blueprint screens (routes) at the captured commit.** A walkthrough step is a Blueprint screen with all its captured views (EkBill's `/bills/[number]` is three bills); the Confirm is refused (409) if the screens were captured again since the page was opened. The building and the Trust report count a screen as signed only when its signature names the Blueprint's commit.
- **Statements are built, not drafted.** The statement a person signs is the traced figures as shown plus the decided cards about the screen, then "I have looked at this screen and it shows what I expect." No model writes it (Invariant 6).

So Procurement Studio is added as a site and gets that session (34 turns, 10 cards); EkBill gets its `docs/DECISIONS.md` at 4f28628 as reconstructed cards (129). Both are flagged `reconstructed`.

Cards are append-only, so the corrected parse added a correction session with 7 new cards and one card superseding the faulty one; 121 identical cards were left alone. The faulty card stays in the record, superseded.

## 2026-10-20 — Stage 1: the Blueprint

- **Schema additions** (additive; MASTER-PROMPT §8 fields unchanged): `BrickNode.envDynamic` (a read of `process.env[x]` the extractor could not name, shown rather than hidden); `ImportEdge.typeOnly` (a type-only import carries no runtime dependency, so screens' import closures skip it); `Commit.changes[].from` (old path of a rename); `Blueprint.worktree`; `Blueprint.unresolved` (internal-looking imports that match no file); `external[].dev` and `external[].manifest` (a monorepo has many manifests).
- **Edges are true; the metric is defined.** A side-effect import (`import './globals.css'`) is an edge with no symbols. The "import edges" figure counts edges that import at least one name, which is what the weekend regex measured (50 on Procurement Studio); side-effect imports are their own figure (1 there). All 51 edges are in the Blueprint.
- **Default imports are recorded as `default`**, the name actually exported, not the importer's local binding (the weekend graph used local names such as `Studio`). The glossary keys them `path#default`.
- **Heaviest brick means heaviest code brick** (JS/TS source). §7.1 calls lib/data.ts (367 lines) the heaviest "text brick, package-lock excluded", but app/globals.css has 401 lines; only the code reading matches the weekend figure.
- **Untested brick** = a non-test code brick that no test file imports directly.
- **`extractedAt` is the committer date** of the extracted commit, not the clock, so re-extraction is byte-identical. `short` is the first 7 characters of the SHA, not git's auto-abbreviation (which grows with the object count and differs between machines).
- **Commit mode reads git's object store**, never the working tree; the same commit is the same Blueprint on any machine.
- **Refs are limited to the extracted history.** Branches and tags are recorded only when their tip is in the history of the extracted commit, so a tag made on a later commit never appears in an older commit's Blueprint. Refs are repository state, not commit content: adding or moving a ref inside that history does change the output, and that is by design (found by the Stage 1 reviewer).
- **`Blueprint.repo` defaults to the origin URL** with credentials and `.git` removed (a token in a remote URL is never written), else the directory name, so the same commit in two differently named checkouts yields the same JSON.
- **This repository carries its own Blueprint through worktree mode.** A file inside a commit cannot name that commit, and history grows with every commit. So `blueprint/self.json` is the working tree on top of a base commit: `HEAD` when changes are pending, otherwise the parent of the last commit that touched a non-excluded path. The file generated before a commit then equals the file regenerated after it, and a commit touching only `blueprint/` changes nothing. Branches and tags are left out of a worktree extraction because they differ between machines (a developer's local branches, CI's checkout).
- **House-stack layer rules match at any depth**, so a monorepo app (`apps/web/app/**`) and a `src/` tree place like a root app. §7.2 names `app/layout*`, `app/page*`, `app/globals.css` for the shell; the default extends that to all of `app/**` outside `app/api/**`, because nested route files are shell too. Lockfiles count as package manifests. Unmatched files go to the shell with the rule `fallback: no rule matched`, so the fallback is visible, never silent.
- **Glossary keys** are a bare symbol or `path#symbol` (the latter wins). An edge's English joins its symbols' phrases and is confirmed only when every symbol has a confirmed phrase.
- **Drafting is separate from extraction.** `extract()` never calls a model; `--draft-glossary` drafts through `packages/model` (prompt `glossary.v1`, builder vendor), writes drafts without a confirmation into the overlay, and never overwrites an existing phrase.
- **The `rama` bin registers tsx** and loads the TypeScript source, consistent with packages being consumed as source.

TypeScript is 6.0.3, not 7: typescript-eslint supports `<6.1`, and the BLUEPRINT.md generator uses the compiler API.
- Packages are consumed as TypeScript source (`exports: ./src/index.ts`); no build step between packages. Scripts run with `tsx`.
- Model adapters call the vendors' HTTP APIs with `fetch` rather than SDKs: one small surface to test and to inject in tests. `call()` takes `role` (builder | auditor), `siteId`, `createdBy` and a zod `output` schema besides `{name, version, input}`, because every row needs a site and a creator and every output must be typed.
- Model per vendor comes from `ANTHROPIC_MODEL` (default `claude-sonnet-5-5`, confirmed in the vendor's model list on 2026-10-20) and `OPENAI_MODEL` (no default: an unverified model name is not guessed).
- A reply cut off at the token limit (Anthropic `stop_reason: max_tokens`, OpenAI `finish_reason: length`) fails at once with `OutputTruncatedError` and is not retried: the same budget would stop it again. Found on the first real OpenAI call, where a reasoning model spent its whole 50-token budget on hidden reasoning and returned an empty reply three times.
- `model_calls.input_tokens` and `output_tokens` are summed over every attempt that got a reply, because every attempt is billed.
- A call that is refused before reaching a vendor (vendor guard, missing model or key, bad prompt name) writes no `model_calls` row; every call that reaches a vendor writes exactly one, success or failure.
- `model_calls` and `audit_log` are append-only from the first migration (a trigger refuses UPDATE, DELETE, TRUNCATE). Drizzle cannot express triggers, so they are appended by hand to the generated `0000_init.sql`; the watcher's drift probe still checks schema against snapshot.
- `next dev` writes `apps/rama/AGENTS.md` and `CLAUDE.md` when it detects an agent. Turned off (`agentRules: false`) so project rules live only in the root `CLAUDE.md`. Its useful content, carried here: Next 16 differs from older training data; the version-matched docs are in `apps/rama/node_modules/next/dist/docs/`.
